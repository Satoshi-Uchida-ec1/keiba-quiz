### 判断と理由

- 仮説（本人記入）: 
- マージ方法は「マージコミット」。Squash や Rebase だと、積んだ次の PR が、すでに入った変更を重複して抱え、競合しやすくなるため。ブランチは、次の PR のベースとして残っているうちに消すと壊れうるので、消していない
- 1 本ごとに `main` で検証した理由は、積んだ PR を 1 本ずつ入れた結果として、`main` が壊れていないことを確かめるため。PR に付いているチェックは Vercel Preview Comments だけで、型・lint・テスト・ビルドは走らない。「CI 成功」は、コードの確認としては何も保証していない（AI が途中の報告で「CI は成功」と書いていたのを、この点で訂正した）
- マージ済みのブランチ（`chore/adopt-mentor-guideline`・`feat/session-algorithm`・`feat/select-screen`・`feat/session-result`・`feat/review`・`feat/top-page`・`chore/extend-deny-rules`）は、リモート・ローカルともに残す。本人の決定で、今後もブランチは消さない方針
- メンターのレビューは、本人の判断でマージ後にまとめて行う。CLAUDE.md の Definition of Done は、`main` への取り込みをレビュー後としている。ここはその順序を、本人が決めて入れ替えた。spec のヘッダ「メンターとの合意」は、引き続き「未」
