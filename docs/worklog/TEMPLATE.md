# worklog 書式（社内メンター制度 v1.1）

ファイル名: `docs/worklog/YYYY-MM-DD.md`。同日の複数セッションは同じファイルに追記する。
セッション終了前に書く。書いていないセッションは未完了。

```markdown
## セッション N（HH:MM 頃）

### 対象

（扱った機能・画面。spec の該当節番号を併記）

### やったこと

（変更したファイルと内容の要約）

### 判断と理由

（迷った点・選んだ選択肢・その理由。「なぜそうしなかったか」も書く。
　AI に聞く前に立てた自分の仮説と、AI の出力をそのまま採用した箇所を明示する）

### 確認したこと

（実行したコマンドと結果。動作確認の方法。鍵・接続文字列・個人名はマスクする）

### [要確認]

（仕様に定義がなく人間の判断が必要な事項。なければ「なし」）

### 次にやること

（次セッションへの引き継ぎ。次の自分がこれだけ読めば再開できる粒度で）
```

## 記入例（「判断と理由」の粒度）

悪い例（理由になっていない）:

> AI が提案したので Spring Security を使った。

最低ライン:

> 仮説: ログインは自前のセッション管理で十分だと思っていた。
> AI に聞いたところ Spring Security を提案された。パスワードのハッシュ化と CSRF 対策を自前で書くと抜けが出やすいので採用。
> 自前セッション管理は却下（spec §3.1 に「将来 SSO 対応」とあり、後で載せ替えが必要になるため）。
> 設定ファイルの中身は出力をそのまま採用した（理解は 5 割）。

「理解は 5 割」のように正直に書いてよい。メンターはそこを面談で埋める。隠すと埋まらない。
